# 架构决策记录（ADR）

> 项目：《冒险家与伙伴》—— 变种贪吃蛇，3D 版
> **本文件是「为什么」的归档。** 规则本身在 `PROMPT.md`，改动边界在 `RULES.md`，命名在 `GLOSSARY.md`。
> 记录时间：2026-09-08 · 决策方式：grilling 六轮追问（**全部待确认项已敲定，无遗留**；ADR-0016 起涉及 AI 自主新增权）

---

## ADR-0001 · 探测优先，但先跑通可玩性再压测

**状态**：已接受

**背景**：本次构建有一明一暗两个目标。明面上的目标是做一个完整的游戏；暗线目标是把它当作探针，评估执行环境在**长会话、大代码量、反复增量修改**下的表现。这两者存在张力：探测要求"故意做重"，可玩性要求"流畅好用"。更关键的是，人工试玩反馈回路（ADR-0006）**依赖游戏真的能玩**——如果游戏卡顿，人工反馈的"手感不好"将无法归因到设计还是性能。

**决策**：分两个阶段，不混做。

- **阶段一（当前）**：代码结构做重（多模块、全量功能、长会话、多轮迭代），但**运行时必须保持 60fps 流畅**。此阶段目标是跑通人工反馈回路。
- **阶段二（后续单独一轮）**：故意制造满载场景（超长队伍、高频粒子、无节制 chunk 生成），主动观察性能极限。

**理由**：阶段二产生的卡顿会污染阶段一的反馈回路。分开做还能得到干净的对照数据——同一环境下 60fps 版与满载版的表现差，才是有效的性能证据。

**后果**：阶段一必须严格禁止任何"为了覆盖度牺牲手感"的实现。性能压测被显式推迟，不在第一版范围内。

## ADR-0002 · 一次做完全量功能，不分阶段裁剪

**状态**：已接受

**背景**：需求包含 8 种伙伴 / 6 种地形 / 4 类怪物 + 3 种 BOSS / 3 个技能 / 无限地图 / 排行榜，是个体量不小的项目。存在"先做最小可玩再迭代"的选项。

**决策**：第一版即交付全部功能，不做功能裁剪。

**理由**：人工是按完整需求试玩并提意见的。若第一版缺内容，人工反馈将集中在"缺什么"而非"什么不好"，反馈回路跑不出有效信号。

**后果与缓解**：第一版代码量大、出错面广。缓解手段是 ADR-0003 的模块划分与参数集中，以及 ADR-0006 的快照反馈机制——出问题时能快速定位而非全局返工。

## ADR-0003 · 生命值采用双资源模型（基础 HP + 护甲层）

**状态**：已接受

**背景**：原始需求同时写了三条规则：① 收集伙伴→生命值+1；② 伙伴数量等同于生命值；③ 遇险自动消耗伙伴。三者合并的实际效果是：**消耗伙伴 = 掉血 = 队伍变短，是同一件事**。由此产生两个问题——玩家进入死亡螺旋（伙伴越少越脆，越脆越容易被消耗）；以及左上角血量与底部伙伴栏永远显示同一个数字，UI 冗余。

**决策**：

- **基础 HP（baseHP）**：独立数值，初始 3，归 0 结束
- **护甲层（armorLayer）**：等于伙伴数量
- **受击结算优先级**：护盾 → 消耗对应伙伴（不掉基础 HP）→ 扣基础 HP
- **UI**：两个数值独立渲染，禁止共用同一数据源

**理由**：保留"伙伴越多越安全"的原始直觉，同时切断死亡螺旋，并让两个 UI 区域各司其职。副作用是新增一个可观测状态变量，对后续调参有利。

**后果**：`state.js` 必须严格区分 `baseHP` 与 `armorLayer`，`collision.js` 的结算分支顺序不可调换。这是全项目最容易写错的地方。

## ADR-0004 · 多文件，参数集中于 config.js

**状态**：**已被 ADR-0008 部分覆盖**（多文件保留，加载方式改为经典 script 标签）

**背景**：同为 HTML 交付，单文件内联（约 2500 行）与多文件模块是两条路。直觉上单文件"更重"，似乎更适合作为压力探针。

**决策**：采用 `index.html` + `js/*.js` + `css/*.css`，约 15 个模块。所有可调参数集中在 `config.js`。

**理由**（反直觉但关键）：单文件看似庞大，实则修改定位极其容易——grep 一次即可命中且行号唯一，**测不出真实难度**。多文件才存在"跨文件追踪依赖、改 A 不误伤 B"的挑战，而这正是人工反馈回路要检验的能力。此外模块边界天然对应术语表条目，使 ADR-0007 的文档真正可用。

**后果**：多文件结构本身保留；但 ES modules 的加载方式被 ADR-0008 替换。

## ADR-0005 · 桌面浏览器 + 键盘为主验证通道

**状态**：已接受

**背景**：原始需求写明"适配手机屏幕且支持触屏滑动操作"，但人工验收环境是电脑屏幕 + 键盘操控。

**决策**：键盘与触屏**双通道都实现**，键盘为主要验证通道，触屏代码保留但标记为「未真机验证」。

**理由**：需求文档的要求不应被静默丢弃；同时触屏在无真机条件下无法验证，诚实标注优于假装完成。

**后果**：触屏的 swipe 阈值、误触处理属于未验证代码。桌面 DevTools 的 touch emulation 可覆盖部分逻辑，但真实触屏延迟与手势误触无法模拟。**在验收人明确放弃触屏前，不得删除 `input.js` 中的触屏分支。**

## ADR-0006 · 人工反馈回路：页面内嵌状态快照 + git 提交链

**状态**：已接受

**背景**：人工反馈的主要形态是主观体感描述（"手感太滑""乌龟触发看不出来"）。这类意见无法直接映射到代码，迭代会卡死在猜测上。同时需要一种方式验证"声称的修改"与"实际的修改"是否一致。

**决策**：两个机制配套。

1. **页面内嵌反馈面板**：右下角常驻按钮，展开后可一键复制运行时状态快照（分数 / baseHP / 伙伴队列 / 状态标记 / config.js 全量参数 / FPS / 设备信息 / 最近 20 条事件日志），并附带意见输入框。
2. **git 提交链**：每个可验证阶段一次 commit，message 写明改了什么、为什么。禁止 `reset --hard` / `push --force` / 改写历史。

**理由**：快照把主观体感转换成客观数据——"太滑"变成 `MOVE_INTERVAL=150ms`，直接可调参。git 则提供可复现的 diff 证据，使"自述的修改"可被核验。

**后果**：`storage.js` 与 `feedback.js` 成为必需的正式模块，不是调试脚手架。事件日志需从第一版就埋点，不能事后补（事后补的日志覆盖不到早期 bug）。

**附带收益**：排行榜与 `sessionCount` 若写入 localStorage，可顺带验证跨会话持久化是否真的生效——关页重开后若打开次数递增，即为持久化成立的直接证据。

## ADR-0007 · 证据固化为 ADR + 术语表，而非交互式报告页

**状态**：已接受（**并由 ADR-0014 扩展为四份文档体系**）

**背景**：前一轮探测曾产出交互式报告页 + PDF/DOCX。本轮选择了独立文档形式。

**决策**：产出 ADR（本文件）与术语表，而非把结论塞进交付页。

**理由**：本项目概念密集（8 伙伴 × 6 地形 × 4 类怪物 × 3 BOSS × 3 技能 × 双资源血量）。命名一旦在多轮迭代中漂移（如"荆棘"写成"尖刺"、"史莱姆"写成"史莱姆怪"），代码与文档将对不上，且**这种漂移在 30 轮后极难发现**。术语表把通用语言固化在磁盘上，使长会话的上下文不再依赖任何一方的记忆。

**后果**：代码标识符必须与术语表严格一致。命名漂移视为违规，需在 review 时纠正。

## ADR-0008 · 渲染改为真 3D，加载方式改为经典 script 标签

**状态**：已接受（覆盖 ADR-0004 的加载方式部分）

**背景**：验收人提出两点：① 自己不懂编程，交付物要能直接打开就玩；② 要 3D 效果。这两点同时推翻了 ADR-0004 的技术选型——ES modules 在 `file://` 协议下会被浏览器 CORS 策略拦截，双击打开必然白屏；而原规格的"Q 版像素 2D"也不再满足诉求。

**决策**：

- 渲染改用 three.js 做真 3D，库文件本地存放于 `vendor/three.min.js`（r128 UMD 版，提供全局 `THREE`），**运行时零外部请求**
- 模块加载从 ES modules 改为**按依赖顺序排列的普通 `<script src>` 标签**，各模块挂载到全局 `window.ADV`
- 多文件结构**保留不变**

**理由**：

- 加载方式：验收人不懂命令行，起本地 server 这个动作对他来说是不可接受的门槛。普通 script 标签在 `file://` 下能正常工作。
- 多文件保留：ADR-0004 想要的"跨文件追踪依赖"难度在经典 script 模式下依然存在，甚至更高——因为依赖关系从显式的 `import` 变成了隐式的加载顺序，改错顺序就会崩。探测价值不降反升。
- 牺牲：失去了显式的 import/export 声明，IDE 的静态分析失效，全局命名空间有冲突风险。用"所有模块必须挂在 `ADV` 下、禁止往 window 直接挂变量"来兜底。

**后果**：`index.html` 里的 script 顺序即依赖顺序，新增模块必须同时更新加载列表（已写进 `RULES.md` L0/L2 的检查项）。three.js 的 UMD 版本停在 r128 附近，较新的 ESM-only 版本不可用。

## ADR-0009 · 技能从 1 个扩展为 3 个，开局全部可用

**状态**：已接受

**背景**：原规格只有冲刺 `dash` 一个技能。验收人在被追问 BOSS 打法时提出："玩家应该有多种技能可选"。同时原需求有个真空：给了怪物血量数值，却没给玩家足够的攻击手段，导致血量形同死数据。

**决策**：三个技能开局全部解锁，各自独立冷却：

- `dash` 冲刺：沿当前方向位移 3 格，位移期间无敌，撞到的怪物 -1 血，CD 10s
- `guard` 护体：2 秒无敌 + 周围 1 格怪物被弹开 2 格，CD 12s
- `slash` 斩击：周围 3×3 所有怪物 -2 血，CD 8s

**理由**：

- 三技能固定而非"局内解锁"或"开局三选一"：验收人需要试玩完整体验才能给出有效反馈。若第一版只能玩到冲刺，他对技能系统的评价会偏。
- 三个技能定位互不重叠：位移逃生 / 防御控场 / 进攻输出。这让怪物血量体系真正成立——玩家有了无伤攻击手段，硬撞的互伤代价才有对比意义（见 ADR-0010）。

**后果**：技能系统从"一个 CD 环"变成"三个 CD 环"，HUD 右上角要容纳三个图标。原"点击或空格触发"改为 `1`/`2`/`3` 键 + 点击图标。

## ADR-0010 · 怪物碰撞改为互伤，并引入撞击硬直

**状态**：已接受（**含已识别风险**）

**背景**：验收人要求"冒险家碰到怪物，怪物也扣血"。原规格里碰撞是单向的——只有玩家受伤，怪物毫发无损。

**决策**：

1. 普通移动撞上怪物：**双方都掉血**。冒险家按该怪物的碰撞伤害值走 ADR-0003 的结算优先级；怪物固定 -1 血
2. 撞击后双方进入 `recoil` 0.5 秒，期间**不再触发**碰撞伤害
3. `dash` 与 `slash` 造成的伤害不触发 `recoil`，也不使冒险家受伤

**理由**：

- 伤害**不对称**是刻意的：如果做成对称互伤（双方各 -1），铁怪（-2）和 BOSS（-3）的威慑力就消失了，它们和小史莱姆的代价一样。玩家吃怪物各自的伤害值，怪物统一掉 1，才能保住"大怪更可怕"的直觉。
- `recoil` 0.5 秒是防止贴脸连撞——没有它，玩家可以用"反复撞击"无脑清怪，怪物血量体系会被这个漏洞打穿。

**已识别风险并接受**：史莱姆只有 1 血，普通撞击即可秒杀，威胁感下降。缓解手段是 0.5 秒硬直（连撞要付出时间代价）+ 冲刺/斩击才是高效清怪手段。**此风险需在试玩时重点验证**——若实测发现游戏过于简单，优先调高史莱姆血量或降低互伤伤害，而不是移除互伤机制。

**后果**：`collision.js` 需要区分"普通移动导致的碰撞"与"技能导致的碰撞"两条路径。`recoil` 与 `stun` 是**不同状态**（前者 0.5 秒僵直，后者撞自身导致的 3 秒失控），已在 `GLOSSARY.md` 中列为命名禁区。

## ADR-0011 · BOSS 从 1 种扩展为 3 种，按波次轮流刷新

**状态**：已接受

**背景**：原规格只有一种 BOSS，行为只有"主动追逐"。验收人要求"多种 boss，每个技能不同"。

**决策**：每 5 分钟刷新 1 只，按 `lavaTitan` → `frostKing` → `shadowLord` 顺序轮换：

| BOSS | 技能 | 设计意图 |
|---|---|---|
| `lavaTitan` 熔岩兽 | 直线突进 + 路径留火痕（3 秒，踩上 -1） | 威胁移动路径，逼玩家绕路 |
| `frostKing` 寒霜王 | 3 格减速光环 + 周期召唤 `slime` | 压缩机动空间，考验技能清场 |
| `shadowLord` 暗影领主 | 短距瞬移接近 + 范围震波（半径 3） | 防风筝，强制玩家留一手 `dash` 或 `guard` |

基础血量与奖励沿用：5 血（每波 +2）、碰撞 -3、击杀 +500 分 + 3 个伙伴。

**理由**：三种技能分别针对"走位 / 空间 / 反应"三种能力，轮换刷新保证每局体验不重复。血量与奖励统一，避免玩家为了奖励而偏好某一种 BOSS。

**后果**：`monsters.js` 需要一个 BOSS 技能调度器，三种行为各自独立实现。BOSS 的波次计数需要跨刷新保持（存在 `state.js`）。

## ADR-0012 · 小狼 wolf 的触发条件敲定（被动，杀怪回血）

**状态**：已接受

**背景**：原需求里 8 种伙伴中 7 种都有明确触发条件，唯独 `wolf` 没写触发时机，只写了效果"移速 +50%，持续 3 秒"。这是长期挂着的待确认项 #1。

**决策**：

- **被动触发**：击杀任意怪物时，若当前 `baseHP < baseHP上限`，自动从队伍**尾部**消耗 1 只 `wolf`，`baseHP` +1。满血时不触发也不消耗
- 原「移速 +50%」效果**取消**

**理由**：验收人原话是"被动触发，杀怪时，有狼没满血，消耗1只狼+1血"。这给了 `wolf` 一个其它 7 种都没有的定位——**唯一具备回复能力的伙伴**。其余伙伴都是"抵挡型"（出事了顶一下），`wolf` 是"续航型"（让你能打得更久）。这个区分让收集策略有了真正的取舍：想要续航就多囤狼，想要保险就多囤抵挡型。

取消移速效果是因为：触发条件从主动变成被动后，"加速"失去了释放时机——被动触发的加速玩家无法控制，体验上更像 bug 而不是能力。

**后果**：`companions.js` 中 `wolf` 的判定不在受击路径上，而在击杀结算路径上，与其它 7 种走不同的代码分支。`WOLF_HEAL_AMOUNT` 进 `config.js`。

## ADR-0013 · 视觉风格：圆润 Q 版低模

**状态**：已接受

**背景**：原需求写的是"Q 版卡通像素风"。验收人在选择 3D 形态时，需要在"纯体素方块风"（像 Minecraft，实现快）和"圆润 Q 版低模"之间取舍。

**决策**：圆润 Q 版低模。角色用球体/胶囊体拼装，大眼睛、高饱和配色、无贴图；地形为方块地块。

**理由**：原需求明确要求"Q 版卡通"，纯体素方块风虽然实现最快，但可爱度不足，与原始诉求不符。地形保持方块是为了让格子边界清晰——这是一款走格子的游戏，玩家必须一眼看清自己在哪一格。角色圆润 + 地块方正，恰好兼顾"可爱"与"可读性"。

**后果**：所有造型由代码用基础几何体拼装（`models.js`），禁止外部模型文件与贴图。禁止用 emoji 充当角色。

## ADR-0014 · 文档体系四层分离，理由与规则分开存放

**状态**：已接受

**背景**：最初的 `PROMPT.md` 自称是"投喂给 coding agent"的开发文档，但里面混了大量解释性文字（例如 §2.7 末尾"为什么不用伙伴数=生命值：那会导致死亡螺旋……"）。这造成两个问题：① 给 AI 的执行指令被解释淹没，容易被带偏；② 但完全删掉理由也有风险——AI 不知道"为什么互伤要设 0.5 秒硬直"，就可能在某次"优化"里把硬直删掉。

**决策**：四份文档各司其职。

| 文档 | 内容 | 受众 |
|---|---|---|
| `PROMPT.md` | 只给事实：规则、数值、模块、验收清单。**不写为什么** | AI 执行时读 |
| `ADR.md` | 只写为什么：每条决策的背景、理由、后果 | 人 + AI 改规则前读 |
| `GLOSSARY.md` | 通用语言与代码标识符，含命名禁区 | 双方，用于防漂移 |
| `RULES.md` | 改动分级、强制动作、自检清单、check 脚本 | AI 每次改完必读 |

**理由**：把"是什么"和"为什么"分开，两边都变干净——执行时不用读理由，改规则时能查到理由。而 ADR-0010 那种"看起来可以优化掉"的设计，因为理由被单独存档，AI 在动它之前会先撞见那条记录。

**后果**：四份文档必须一起投喂，缺一份 AI 就会在命名或改动边界上出错（已在 `PROMPT.md` 开头写明）。任何改动都要检查是否触发文档同步责任（`RULES.md` §9）。

## ADR-0015 · 硬性规定配机器校验，不靠 AI 自觉

**状态**：已接受

**背景**：`RULES.md` 里的 L0 禁令如果只写在纸上，换一个 AI 会话就可能失效——新会话看不到上一轮的承诺。

**决策**：配一个 `check.js`，每次 commit 前用 Node 跑一遍，检查 8 项（文件是否被合并、是否混入 ES modules 语法、是否有外部请求、是否出现命名禁区词、是否有写死的魔法数字、`index.html` 加载列表是否完整、全局命名空间是否干净、改动是否已 commit）。

**理由**：把约束从"AI 的自我承诺"变成"跑不过就报错"，才能在换会话、换模型时依然生效。同时它不进游戏运行时、不算构建工具，不违反 ADR-0008。

**后果**：check 脚本本身可以持续改进（L2），但它判定的规则属于 L1——改判定标准要先说明。第 5 项（魔法数字）最容易误报，误报时加白名单并在 ADR 记一笔，**不许为了过检查而改代码**。

## ADR-0016 · 赋予 AI 自主新增权，以四条红线为对价

**状态**：已接受（**含内部冲突与处理方式**）

**背景**：验收人从第一次提需求起就在说"让 AI 优化或增加功能"。但在前四轮追问中，文档体系实际上把新增内容列为 L1 需批准事项（`RULES.md` 原 L1-7），甚至讨论过用 `check.js` 做"清单外即报错"的越权拦截。追问到 Q20 时验收人明确否决："**就是要求 AI 自己加！！！**"——他要的是自主权，不是拦截。

**决策**：

1. **AI 有权自主新增**伙伴 / 地形 / 怪物 / 技能 / 功能，无需事先申请。何时加、加什么、加多少，由 AI 自己判断
2. **四条内容红线（L0-A ~ L0-D）**是全部对价：不改旧数值、不加按键、不改结算顺序、不改 UI 布局
3. **六件套**：config 参数（含 `enabled` 开关）/ 术语表条目 / 造型定义 / 克制关系 / 三步验证 / ADR
4. **强度对比表**：数值不设上限，但必须与现有同类逐项对比，超中位处标 `⚠️`
5. **可关闭开关**：每个新增实体必须有独立 `enabled` 开关，关掉即完全移除
6. **报告义务 = 只更新内容总表**（`PROMPT.md` §9.3），不单独写报告

**理由**：

- **为什么不设数值上限**：设上限（新伙伴不得强于现有最强）会直接掐死创新——AI 只能加越来越弱的东西。改用"强度对比表 + 可关闭开关"，把判断权交还给验收人的实际体验：加得不好，改一行关掉，比事先审批更有效率。
- **为什么红线是这四条**：它们保护的都是**已经稳定下来的东西**——旧数值背后是验收人调过的手感记录，按键与 UI 布局背后是他的肌肉记忆，结算顺序是全项目最容易写错的地方。新增可以激进，但已定型的部分不许动。
- **为什么报告义务这么轻**：验收人明确选择"不单独报，只更新总表"。总表因此成为唯一监督入口，它必须能一眼看全（含 config 开关名与三步验证），这也是 §9.2/§9.3 把原生与新增都列出来的原因。

**内部冲突与处理**：Q17 选定「数据层可自主、逻辑层禁止」，Q21/Q22 又选定「AI 全自动」，二者矛盾。处理方式是把**分层从"批准门槛"降级为"实现方式约束"**——AI 依然全自动，但若新增需要写新逻辑（现有 5 种伙伴效果类型装不下），必须在 ADR 里额外说明「现有类型为什么装不下」。不拦截，只留痕。

**后果**：

- `check.js` 第 9 项（总表与代码实体清单比对）**刻意设计为警告而非阻断**——用一个脚本把自主权堵死，等于推翻本决策
- `PROMPT.md` 新增 §9 内容总表章节（原生清单 + AI 新增登记处 + 效果类型枚举）
- `GLOSSARY.md` 新增第九节，固化 15 个效果类型标识，防止新增时各起各的名字
- 原生 24 个实体的清单被显式冻结为"原生"，与后续 AI 新增区分开（L0-A 的具体边界）

## ADR-0017 · 给每一类内容立「本质约束」

**状态**：已接受

**背景**：验收人提出「伙伴都是被动能力」，并指出新增伙伴、技能、地形都需要各自的约束。检查后发现这是一个真实的文档缺口：`GLOSSARY.md` 里 8 种伙伴只有 `wolf` 标了「被动」，其余 7 种写的是「进入 X 地形」这类触发条件——**触发条件恰好都是被动的，这是巧合被当成了默认**。文档里从来没有一条规则禁止 AI 新增一个"点击释放"的伙伴，而那不违反当时任何一条规定。

**决策**：为五类内容各立本质约束，级别为 L0-E（红线）：

| 类别 | 本质约束 |
|---|---|
| 伙伴 | 一律被动触发，玩家永不主动释放；效果一次性；从尾部消耗；不占技能键 |
| 技能 | 必须主动释放；必须有独立冷却；不消耗伙伴；不占队伍位；只能占 `1`/`2`/`3` 或 HUD 点击 |
| 地形 | 静态或周期性变化；可被摧毁；踩上才生效；必须写明克星；不得聚堆、不得形成屏障 |
| 普通怪 | 有血量；会自主行动；可被击杀；有明确碰撞伤害 |
| BOSS | 满足怪物全部约束；至少一个技能；技能必须可躲；按波次刷新 |

**理由**：现有设计里藏着一根轴——**伙伴被动、技能主动**。把它写出来，AI 新增时就不会造出「到底是伙伴还是技能」的四不像。同理，"会动的、有血量的"是怪物，"不会动的、能被摧毁的"是地形——这两条轴一起，覆盖了绝大多数分类歧义。

**后果**：判据被简化成三句问答写进文档（玩家能不能主动放？它会不会动？它有没有血量？）。AI 自主新增时必须自查这三问（已进 `RULES.md` §4 自检清单）。

## ADR-0018 · 实体删减与五处机制变更

**状态**：已接受

**背景**：在讨论"地形生成原则"时，验收人一次性提出了多项调整，涉及实体删减与机制变更。

**决策**（五项）：

1. **移除 `fog` 迷雾地形与 `owl` 猫头鹰伙伴**、**移除 `trap` 陷阱地形与 `rabbit` 兔子伙伴**。地形 6→4 种，伙伴 8→6 种。空缺不补，交由 AI 自主新增填补（ADR-0016）
2. **伙伴触发 = 摧毁地形**：`dragon` / `phoenix` / `fox` 触发时，除消耗伙伴外，**该格地形永久变为 `grass`**（当前 chunk 生命周期内）。措辞从"安全通过"改为"摧毁"
3. **摧毁途径扩展为三种**：伙伴触发 / `slash` 斩击（周围 3×3）/ BOSS 技能（`lavaTitan` 突进路径、`shadowLord` 震波范围）
4. **无对应伙伴踩危险地形追加 1 秒眩晕**：原为只扣血。撞自身仍是 3 秒，两者参数分离（`STUN_DURATION: 3000` / `TERRAIN_STUN_DURATION: 1000`）
5. **护盾改为「临时一格血」**：验收人的原话定义——"相当于临时的一格血，不是无敌，不叠加但是重置时间"。`SHIELD_POINTS: 1`、`SHIELD_DURATION: 60000`。受击时护盾先吸收 1 点，溢出伤害继续打 `baseHP`

**理由**：

- **删减两组**：迷雾/猫头鹰与陷阱/兔子在机制上是孤立的——它们不参与伤害体系，只做"视野"和"一次性扣血"，而后者与火山、荆棘重复。删掉后地形收敛为三种可摧毁的威胁，伙伴定位也收敛为"摧毁地形型 / 战斗型 / 续航型"三类，认知负担明显下降。
- **伙伴摧毁地形**：这是验收人的原话——"凤凰进入冰川地形，本质就是消耗凤凰摧毁地形"。它把伙伴从"挡伤害的消耗品"变成"开路的铲子"，给了收集行为一个正反馈（地图越走越干净），也让"安全通过"这个含糊措辞落地为可观测的状态变化。
- **地形追加眩晕**：踩地形是最高频的失误，只扣血不足以形成记忆。1 秒而非 3 秒，是为了避免与撞自身同罚——一次失误连锁送命的挫败感远大于教育价值。
- **护盾改为临时一格血**：原设计是"抵消任意一次伤害、持续 3 秒"，它是一个开关——要么全免，要么没有。改成"临时的一格血"后，护盾成为血条的一部分，玩家能直观理解"我多挨一下"。不叠加是为了防止囤积，重置时间保证持续获取熊猫仍有价值。溢出伤害继续打 `baseHP` 这一点很关键——它让护盾区别于 `dash` / `guard` 的**无敌**，避免玩家误以为有盾就可以硬闯 BOSS。

**已识别风险并接受**：

- 地形可被摧毁会让游戏**越往后越安全**。缓解：地图无限延伸，新 `chunk` 持续生成新危险地形；且摧毁需要消耗伙伴，伙伴是稀缺资源。需在试玩时验证后期是否过于轻松。
- 砍掉两组实体后，克星关系从 5 组减到 3 组，伙伴的策略深度下降。缓解手段是 AI 自主新增补位（ADR-0016），且新增必须遵守 ADR-0017 的类约束。

**后果**：

- 地形权重重新分配为 `grass: 76, volcano: 8, glacier: 8, thorn: 8`（原危险地形合计 24% 的密度保持不变，只是从四种摊到三种）
- 伙伴权重重新分配为 `fox: 20, turtle: 20, wolf: 20, dragon: 13, phoenix: 13, panda: 14`
- 原生实体从 24 个减为 21 个，`PROMPT.md` §9.2 清单已更新，移除的四个标识列入 `GLOSSARY.md` 命名禁区（不得复用）
- 效果类型枚举同步更新：`PASS` → `DESTROY_TERRAIN`，移除 `REVEAL` 与 `OBSCURE`，新增 `CYCLIC`
- 地形生成新增四条原则：不聚堆（3×3 邻域内同类 ≤ 2）/ 不形成屏障 / 动态无边界 / 出生点 5×5 安全

## 原待确认项：全部敲定

上一轮列出的 6 个待确认项已全部关闭，最终采纳如下。

| # | 问题 | 最终采纳 | 出处 |
|---|---|---|---|
| 1 | 小狼触发条件 | **被动**：击杀怪物且未满血时，消耗 1 只狼 +1 血。原移速效果取消 | ADR-0012 |
| 2 | 铁怪移动方式 | **极慢巡逻**（每 2 秒 1 格），不追逐。它伤害 2 点，定位是路障 | `PROMPT.md` §2.6 |
| 3 | 收集分是否按稀有度加权 | **加权**：普通 10 分，稀有（龙/凤凰/熊猫）×2 = 20 分 | `PROMPT.md` §2.10 |
| 4 | 击杀普通怪是否加分 | **加**：史莱姆 20 / 弓箭手 50 / 铁怪 100 | `PROMPT.md` §2.10 |
| 5 | 触屏是否仍需实现 | **实现并标注未真机验证**。键盘为主通道，触屏不得影响键盘手感 | ADR-0005 |
| 6 | BOSS 击杀方式缺失（原为阻塞级） | **被整体替代**：不再是"冲刺撞 5 次"，而是四种手段并存——普通撞击互伤 -1、`dash` -1 且无伤、`slash` -2 且无伤、`guard` 弹开。同时 BOSS 扩展为 3 种 | ADR-0009 / 0010 / 0011 |

> **关于 #6 的演变值得记一笔**：它原本是需求真空（给了血量没给攻击手段），建议方案是"冲刺撞 5 次"。追问中验收人提出"玩家该有多种技能"，这个建议方案随即被推翻——单一手段撞 5 次太单调，且让冲刺 CD 成为唯一瓶颈。最终用"三技能 + 互伤"整体替代，既修好了血量体系，也让 BOSS 战有了节奏。
